# 基于微信小程序的花卉商城系统设计说明

## 1. 项目定位

本项目以 CRMEB Java 3.1 单商户商城为基础，二次开发一个面向单个实体花店的同城配送商城。顾客通过微信小程序完成选花、下单、预约配送和售后；花店员工通过 Web 管理后台维护商品并处理制作、配送和售后业务。

本项目用于毕业设计，展示方式以微信开发者工具、浏览器和论文截图为主，不要求正式发布微信小程序，也不要求接入真实微信支付或实时骑手定位。

论文题目为“基于微信小程序的花卉商城系统开发与设计”。核心创新点集中在以下三个模块：

1. 花卉商品与场景化分类。
2. 同城预约配送与时段容量控制。
3. 花束制作及配送履约流程。

## 2. 原项目情况

### 2.1 原有结构

原项目包含：

- `backend/crmeb-front`：微信小程序和移动商城接口。
- `backend/crmeb-admin`：Web 管理后台接口。
- `backend/crmeb-service`：商城公共业务服务。
- `backend/crmeb-common`：实体、请求对象、常量和公共工具。
- `frontend/uni-app`：微信小程序、H5 和 App 共用的移动端代码。
- `frontend/admin`：Vue 3 与 Element Plus 管理后台。
- `frontend/pc`：没有完整的顾客 PC 商城，不纳入本项目。

### 2.2 可复用能力

项目继续使用原有商品、SKU、分类、购物车、订单、支付、退款、优惠券、会员、积分、评价、收藏、门店自提、消息通知、首页装修、权限和统计能力。

原有砍价、拼团、秒杀和分销模块保留代码，但从本项目的默认菜单与小程序首页中隐藏，避免干扰花店主题和答辩演示。

## 3. 系统角色

### 3.1 顾客

顾客使用微信小程序浏览鲜花、填写送花信息、预约配送、模拟支付、查看制作和配送进度、申请售后及发表评价。

### 3.2 花店管理员

管理员使用 Web 后台维护商品、配送区域和配送时段，处理订单、制作、配送、售后、会员、页面装修和经营统计。

### 3.3 花店员工

员工使用受限的 Web 后台账号处理分配给自己的制作或配送任务。员工不能修改系统配置、管理员权限和财务设置。

## 4. 功能范围

### 4.1 微信小程序端

#### 商城基础功能

- 微信登录、个人资料和收货地址。
- 首页、分类、搜索和场景化筛选。
- 商品详情、规格选择、收藏和购物车。
- 优惠券、会员积分、订单列表和商品评价。
- 资讯列表、花艺文章和鲜花养护知识。

#### 花店特色功能

- 按适用场景、赠送对象、颜色和预算筛选鲜花。
- 展示主要花材、花语、枝数、包装方式和养护说明。
- 分别填写订花人和收花人的姓名与电话。
- 选择配送区域、配送日期和配送时间段。
- 填写贺卡祝福语并选择是否匿名送花。
- 选择是否需要提前联系收花人。
- 选择花材缺货处理方式：接受同色同价替换、替换前联系或不接受替换。
- 选择同城配送或到店自提。
- 使用模拟微信支付完成演示订单。
- 查看待接单、待制作、制作中、待配送、配送中和已送达进度。
- 查看花束成品照和送达凭证。
- 申请鲜花品质售后并上传图片。

### 4.2 Web 花店管理后台

#### 经营首页

- 今日销售额、今日订单数和客单价。
- 待接单、待制作、待配送和售后数量。
- 近期销售趋势和热销鲜花排行。
- 配送准时率和热门配送时段。

#### 花卉商品

- 商品分类、SKU、价格、库存、主图和轮播图。
- 花材、花语、适用场景、赠送对象、颜色和养护说明。
- 商品上架、下架、推荐和排序。

#### 花店订单

- 查询和查看送花订单完整信息。
- 接单、备料、开始制作和完成制作。
- 上传花束成品照片。
- 填写配送人员、联系电话和配送备注。
- 上传送达凭证并完成订单。
- 打印花艺制作单和配送单。

#### 配送管理

- 配送区域、起送金额和配送费用。
- 配送日期、时间段、接单上限和停止预约时间。
- 临时关闭某个日期或时间段。
- 查看各时间段已预约数量。

#### 售后管理

- 处理不新鲜、花材不符、包装破损和配送超时问题。
- 查看顾客上传的售后图片。
- 同意、拒绝或人工协商退款申请。
- 保存售后处理意见和操作记录。

#### 运营与系统

- 用户、会员等级、积分、标签和优惠券。
- 首页装修、轮播图、花艺资讯和养护文章。
- 管理员、员工、角色权限、门店信息和消息配置。
- 销售、商品、会员、订单和配送统计。

## 5. 视觉设计

### 5.1 总体风格

商城采用高端实体花店与花艺杂志结合的风格。真实花束摄影是主要视觉内容，界面使用较大留白和克制的中英文排版，不使用通用电商的大量彩色标签、渐变和厚重阴影。

视觉原型中的“花屿 / FLORA ISLAND”是演示品牌名。最终品牌名通过系统设置维护，不写死在业务代码中。

### 5.2 色彩

- 主色：军绿色 `#35402F`。
- 深色：深橄榄绿 `#243129`。
- 背景色：暖白色 `#F7F4EC`。
- 内容底色：纸张白 `#FFFEFA`。
- 正文色：墨灰色 `#2D312C`。
- 强调色：重点红 `#ED3C2D`。

重点红只用于商品价格、购物车数量、异常提示和关键购买按钮，不作为大面积背景。

### 5.3 字体

- 中文标题使用宋体或系统可用的中文衬线字体。
- 英文标题使用 Georgia 等衬线字体，并适当增加字间距。
- 正文和操作文字使用系统无衬线字体，保证小程序可读性。

### 5.4 首页结构

首页采用连续长页：

1. 全屏花艺品牌主视觉。
2. 每周上新。
3. 鲜花分类导航。
4. 按预算选花。
5. 品牌故事。
6. 人气精选大图模块。
7. 专属定制花礼。
8. 双列产品推荐。
9. 花店服务保障。
10. 首页、分类、购物车和个人中心底部导航。

### 5.5 商品图片与卡片

- 首页商品使用双列方形图片，卡片无边框、无厚重阴影。
- 分类页使用左图右文的横向清单，提高浏览密度。
- 商品详情页使用沉浸式大图，图片区域只显示鲜花图片，不包含价格、促销或其他文字。
- 商品价格、名称、销量和配送信息位于图片下方独立内容区域。
- 商品详情底部提供“加入购物车”和“立即购买”操作。

### 5.6 Web 后台换肤

管理后台保留 Element Plus 的清晰结构，使用军绿色作为导航与主操作色，重点红只用于警告、退款和关键数值。后台以效率为主，不照搬小程序的大图杂志布局。

## 6. 系统结构

系统继续采用前后端分离方式：

- 微信小程序调用 `crmeb-front` 接口。
- Web 管理后台调用 `crmeb-admin` 接口。
- 两个接口服务共用 `crmeb-service` 业务层和 `crmeb-common` 公共模型。
- MySQL 保存永久业务数据。
- Redis 保存登录状态、热点数据和临时订单信息。
- 原有附件系统保存商品图、评价图、成品照和配送凭证。

新增业务在原有商城骨架中划分为三个独立模块：

1. 花卉商品服务：处理花材、花语、场景、对象和养护说明。
2. 预约配送服务：处理区域、费用、日期、时段、容量和截单规则。
3. 花店履约服务：处理接单、制作、配送、凭证和状态记录。

## 7. 数据库设计

### 7.1 复用的数据表

- `eb_store_product`：商品基本信息。
- `eb_store_product_attr_value`：SKU、价格和库存。
- `eb_store_order`：订单、金额、支付和主状态。
- `eb_store_order_info`：订单商品快照。
- `eb_user`：用户资料。
- `eb_user_address`：常用地址。
- `eb_store_product_reply`：商品评价。
- `eb_store_coupon`：优惠券。

### 7.2 新增数据表

#### eb_flower_product_ext

一条记录对应一个原商城商品，保存：

- `product_id`：原商品编号，唯一关联。
- `flower_materials`：主要花材。
- `flower_language`：花语。
- `occasion`：适用场景。
- `recipient`：赠送对象。
- `color_series`：色系。
- `care_tips`：养护说明。

#### eb_flower_delivery_zone

保存花店同城配送范围：

- `zone_name`：区域名称。
- `area_codes`：覆盖的区县或街道编码。
- `delivery_fee`：配送费。
- `minimum_amount`：起送金额。
- `enabled`：是否启用。

#### eb_flower_delivery_slot

保存可预约的配送日期与时间段：

- `delivery_date`：配送日期。
- `start_time`、`end_time`：时间段。
- `capacity`：最大接单量。
- `booked_count`：当前占用量，包含未过期的待付款订单。
- `cutoff_time`：停止预约时间。
- `enabled`：是否启用。

#### eb_flower_order_ext

一条记录对应一个原商城订单，保存：

- `order_id`：原订单编号，唯一关联。
- `sender_name`、`sender_phone`：订花人。
- `recipient_name`、`recipient_phone`：收花人。
- `delivery_address_snapshot`：下单时的配送地址快照。
- `delivery_zone_id`：配送区域。
- `delivery_date`、`slot_id`：预约日期与时间段。
- `greeting_card`：贺卡祝福语。
- `anonymous`：是否匿名。
- `contact_recipient`：是否提前联系收花人。
- `substitution_policy`：缺货换花处理方式。
- `reservation_expire_time`：未付款预约失效时间。

#### eb_flower_order_progress

一笔订单可有多条记录，保存：

- `order_id`：关联订单。
- `stage`：业务阶段。
- `operator_id`：操作员工。
- `proof_image`：成品照或送达凭证。
- `remark`：操作备注。
- `create_time`：操作时间。

### 7.3 订单状态兼容

原 `eb_store_order` 继续管理支付、发货、收货、完成和退款等商城主状态。新增履约表管理待接单、待制作、制作中、待配送和配送中等花店细分状态。

- 未付款：原订单支付标识为未支付。
- 支付后至待配送：原订单保持待发货，细分状态保存在履约表。
- 配送中：原订单进入已发货/待收货状态。
- 顾客确认或管理员完成送达：原订单进入待评价状态。
- 评价或自动完成后：原订单进入已完成状态。

这种设计避免修改原支付、退款和订单统计的核心逻辑。

## 8. 核心业务流程

### 8.1 正常送花流程

1. 顾客选择鲜花与规格。
2. 填写订花人、收花人、贺卡和换花选择。
3. 选择配送区域、日期和时间段。
4. 系统再次检查服务范围、起送金额和时间段容量。
5. 创建待付款订单，占用配送名额 15 分钟。
6. 顾客完成模拟支付，订单进入待接单。
7. 管理员接单，订单进入待制作。
8. 花艺师开始制作并可上传成品照。
9. 制作完成后进入待配送。
10. 管理员填写配送人员，订单进入配送中。
11. 上传送达凭证并完成送达。
12. 顾客确认收花、评价或申请售后。

### 8.2 配送容量

创建订单前使用数据库事务和条件更新再次检查 `booked_count < capacity`，防止多个顾客同时抢占最后一个名额。创建订单成功后增加占用量；待付款订单超过 15 分钟自动取消并减少占用量。已支付订单取消后同样释放容量。

### 8.3 花材缺货

- 接受同色同价替换：管理员记录替换内容后继续制作。
- 替换前联系：管理员联系顾客并记录处理结果。
- 不接受替换：管理员取消订单并执行模拟退款。

### 8.4 取消与退款

- 制作前：顾客可申请取消，管理员同意后退款并释放时段。
- 制作后：顾客不能直接取消，必须由管理员根据花材损耗人工处理。
- 任何订单不能重复退款或在错误状态下退款。

### 8.5 品质售后

顾客在送达后 2 小时内可选择不新鲜、花材不符、包装破损或配送超时，并上传图片。超过 2 小时后普通品质售后入口关闭，转为联系客服人工处理。

### 8.6 状态安全

后台只允许订单按规定顺序流转，不允许未完成制作直接配送。每次状态变更都记录操作人、时间和备注。重复请求返回当前状态，不重复执行库存、容量或退款操作。

## 9. 模拟第三方能力

### 9.1 模拟微信支付

开发环境提供模拟支付开关。模拟支付必须走与真实支付成功相同的内部订单处理入口，确保订单状态、销量、时段容量和通知逻辑一致。生产配置默认关闭模拟支付。

### 9.2 地图与配送

小程序只展示门店位置、顾客配送地址和简单导航入口。配送范围按后台维护的行政区域判断，不开发骑手实时轨迹和智能路线规划。

## 10. 错误处理

- 地址不在配送范围：禁止提交并提示选择自提或其他地址。
- 未达到起送金额：展示还差的金额。
- 配送时段已满或已截单：刷新可选时段，要求重新选择。
- 订单预约已过期：取消订单并释放名额。
- 商品下架或库存不足：返回购物车并提示失效商品。
- 订单状态不允许操作：拒绝请求并显示当前正确状态。
- 图片上传失败：保留已填写内容，允许重新上传。
- 模拟支付失败：订单保持待付款，不重复创建订单。
- 后台无权限：拒绝操作并记录安全日志。

## 11. 测试与验收

### 11.1 完整演示流程

最终必须能够从小程序选花开始，完成送花信息、预约时段、模拟支付、后台接单、制作、配送、送达、评价或售后的连续演示。

### 11.2 核心测试

- 花卉商品扩展信息新增、修改和查询。
- 场景、对象、颜色和预算筛选。
- 配送范围、配送费和起送金额计算。
- 配送时段容量占用、满额限制和超时释放。
- 待接单到已完成的状态顺序。
- 重复支付、重复接单和越级状态操作拦截。
- 三种花材替换策略。
- 制作前后不同的取消规则。
- 鲜花品质售后两小时时限。
- 管理员与员工权限隔离。
- 小程序与后台展示的数据一致性。
- 后端、微信小程序端和 Web 后台能够正常构建。

### 11.3 答辩材料

准备小程序首页、分类、商品详情、送花信息、配送时段、模拟支付、订单进度、配送凭证、评价售后、后台订单看板、销售统计、系统结构图、数据库关系图、订单流程图和测试结果截图。

## 12. 非本期范围

本期不开发：

- 多商户入驻与商家结算。
- 顾客 PC 商城。
- 真实骑手定位与轨迹。
- 供应商、采购入库和花材批次管理。
- 花束配方与花材级自动扣减。
- 企业月结、婚庆项目和周期订花。
- 正式微信支付上线与交易类小程序发布流程。

## 13. 完成标准

项目完成必须同时满足：

1. 小程序与 Web 管理后台使用已确认的花店视觉风格。
2. 首页长页结构、字体、颜色和商品卡片符合设计。
3. 五张花店业务表及对应功能可用。
4. 顾客下单到花店送达的完整流程可以演示。
5. 配送容量、订单状态、取消和售后异常规则经过测试。
6. 原商城支付、订单、会员和权限主流程不被破坏。
7. 毕业论文需要的主要页面、图表和测试结果可以截图。
